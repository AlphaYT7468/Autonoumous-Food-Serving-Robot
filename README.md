# dev_ws — Autonomous Differential-Drive Robot (ROS 2 Humble)

A complete ROS 2 workspace for a two-wheeled differential-drive mobile robot that
maps and autonomously navigates an indoor environment. It runs on real hardware
(Arduino motor controller + RPLIDAR) and in Gazebo simulation from the same robot
description.

The mapped environment included here is a mechatronics lab, captured with
`slam_toolbox`.

| | |
|---|---|
| **ROS 2 distro** | Humble Hawksbill |
| **OS** | Ubuntu 22.04 LTS |
| **Build system** | `colcon` / `ament_cmake` |
| **Localisation & mapping** | `slam_toolbox` (async, serialised pose-graph) |
| **Navigation** | Nav2 |
| **Motion control** | `ros2_control` + `diff_drive_controller` |
| **Laser** | Slamtec RPLIDAR |

## Hardware

The robot description and controller config are tuned to this specific chassis.
If your robot differs, these are the numbers to change.

| Parameter | Value | Defined in |
|---|---|---|
| Wheel radius | 0.0415 m | `description/robot_core.xacro` |
| Wheel separation (track) | 0.331 m | `config/my_controllers.yaml` |
| Wheel thickness | 0.026 m | `description/robot_core.xacro` |
| Chassis (L×W×H) | 0.305 × 0.265 × 0.138 m | `description/robot_core.xacro` |
| Caster offset (x) | 0.27 m | `description/robot_core.xacro` |
| Encoder counts per rev | 3835 | `description/ros2_control.xacro` |
| Motor controller port | `/dev/ttyUSB0` @ 57600 baud | `description/ros2_control.xacro` |
| LIDAR port | `/dev/ttyUSB1` @ 115200 baud | `launch/rplidar.launch.py` |
| LIDAR mount (x, y, z) | 0.05, 0, 0.316 m from chassis | `description/lidar.xacro` |
| Control loop rate | 30 Hz | `description/ros2_control.xacro` |
| Odometry publish rate | 50 Hz | `config/my_controllers.yaml` |

The motor controller is driven through the `diffdrive_arduino/DiffDriveArduino`
`ros2_control` hardware interface, which speaks a simple serial protocol to an
Arduino running encoder-feedback PID.

### Frames

```
map ──(slam_toolbox)──> odom ──(diff_cont)──> base_link ──> chassis ──> laser_frame
                                                                   └──> camera_link
                                          └──> left_wheel / right_wheel / caster
```

### Launch files

| File | Purpose |
|---|---|
| `bringup.launch.py` | **Main entry point.** Full autonomous stack on real hardware: drivers → lidar → SLAM localisation → Nav2 → RViz, started in a staggered sequence. |
| `launch_robot.launch.py` | Real-robot base: `robot_state_publisher`, `controller_manager`, `diff_cont`, `joint_broad`, `twist_mux`. |
| `launch_sim.launch.py` | Gazebo simulation equivalent. |
| `rsp.launch.py` | `robot_state_publisher` only (processes the xacro into `/robot_description`). |
| `rplidar.launch.py` | RPLIDAR driver → `/scan`. |
| `online_async_launch.py` | `slam_toolbox` async node (mapping **or** localisation, see below). |
| `navigation_launch.py` | Bundled Nav2 copy — **superseded**, see [Known issues](#known-issues). |
| `localization_launch.py` | AMCL-based localisation (alternative to slam_toolbox localisation). |
| `joystick.launch.py` | `joy` + `teleop_twist_joy` → `/cmd_vel_joy`. |
| `camera.launch.py` | Camera driver. |
| `ball_tracker.launch.py` | Colour-blob ball tracking demo → `/cmd_vel_tracker`. |

### Velocity multiplexing

`twist_mux` arbitrates between three command sources, highest priority wins:

| Source | Topic | Priority |
|---|---|---|
| Joystick | `/cmd_vel_joy` | 100 |
| Ball tracker | `/cmd_vel_tracker` | 20 |
| Nav2 | `/cmd_vel` | 10 |

Output goes to `/diff_cont/cmd_vel_unstamped`. Each input times out after 0.5 s,
so releasing the joystick hands control back to Nav2.

### Source dependencies

Clone these into `src/` alongside `articubot_one`:

```bash
cd ~/dev_ws/src
# Arduino hardware interface for ros2_control
git clone https://github.com/joshnewans/diffdrive_arduino.git
git clone https://github.com/joshnewans/serial.git
# Optional: only needed for ball_tracker.launch.py
git clone https://github.com/joshnewans/ball_tracker.git
```

> `diffdrive_arduino` and `serial` are **required** for the real robot —
> without them `controller_manager` cannot load the `RealRobot` hardware
> plugin. They are not needed for simulation.

### Arduino firmware

The motor controller expects [`ros_arduino_bridge`](https://github.com/joshnewans/ros_arduino_bridge)
style firmware: a serial protocol with encoder reads and PID motor commands at
57600 baud. Flash this to the Arduino before running on hardware.

## Build

```bash
cd ~/dev_ws
source /opt/ros/humble/setup.bash
colcon build --symlink-install
source install/setup.bash
```

Add the workspace to every new shell:

```bash
echo "source ~/dev_ws/install/setup.bash" >> ~/.bashrc
```

> `--symlink-install` means edits to launch files, YAML and xacro take effect
> without rebuilding. Adding or removing files still needs a rebuild.

## Running the robot

### Full autonomous stack

```bash
ros2 launch articubot_one bringup.launch.py
```

This brings everything up in a staggered sequence so each layer has its
dependencies ready:

| t | Component |
|---|---|
| 0 s | `launch_robot.launch.py` — state publisher, controllers, twist_mux |
| 0 s | `rplidar.launch.py` — laser scans on `/scan` |
| 10 s | `slam_toolbox` — loads the saved map, publishes `map` → `odom` |
| 20 s | Nav2 — planner, controller, behaviour server |
| 20 s | RViz with `config/main.rviz` |

Once RViz is up:

1. Wait for the map of the lab to appear and the robot to localise onto it.
2. If the robot pose looks wrong, use **2D Pose Estimate** to correct it.
3. Click **2D Goal Pose** and pick a destination — Nav2 plans and drives there.

### Serial port permissions

The two USB devices must be readable without root:

```bash
sudo usermod -aG dialout $USER   # log out and back in for this to take effect
ls -l /dev/ttyUSB*               # confirm both devices are present
```

`/dev/ttyUSB0` must be the Arduino and `/dev/ttyUSB1` the LIDAR. USB enumeration
order is **not** guaranteed across reboots — see [Troubleshooting](#troubleshooting)
for stable device names.

### Manual driving

```bash
# Keyboard
ros2 run teleop_twist_keyboard teleop_twist_keyboard --ros-args -r /cmd_vel:=/cmd_vel_joy

# Gamepad (hold the enable button — button 6 — as a deadman switch)
ros2 launch articubot_one joystick.launch.py
```

## Running in simulation

No hardware required:

```bash
ros2 launch articubot_one launch_sim.launch.py world:=./src/articubot_one/worlds/obstacles.world
```

Then in a second terminal, for mapping in sim:

```bash
ros2 launch articubot_one online_async_launch.py use_sim_time:=true
```

> Note the `use_sim_time` flip: `online_async_launch.py` now defaults to
> `false` for real-hardware use, so simulation must pass `true` explicitly.

## Mapping a new area

The saved lab map lives in `maps/`. To map somewhere new:

**1.** Open `config/mapper_params_online_async.yaml` and switch to mapping mode:

```yaml
mode: mapping          # was: localization
# comment out map_file_name so it starts from a blank map
# map_file_name: /home/alphayt/dev_ws/maps/mechatronics_lab_serial
```

**2.** Start the base, lidar and SLAM:

```bash
ros2 launch articubot_one launch_robot.launch.py
ros2 launch articubot_one rplidar.launch.py
ros2 launch articubot_one online_async_launch.py
rviz2 -d src/articubot_one/config/main.rviz
```

**3.** Drive slowly around the space with the joystick or keyboard until the map
is complete. Revisit places you have already been so loop closure can tighten
the pose graph.

**4.** Save the result. Use the **SlamToolboxPlugin** panel in RViz, or:

```bash
# Occupancy grid (.pgm + .yaml) — for Nav2 / map_server
ros2 run nav2_map_server map_saver_cli -f ~/dev_ws/maps/my_new_map_save

# Serialised pose graph (.data + .posegraph) — for slam_toolbox localisation
ros2 service call /slam_toolbox/serialize_map slam_toolbox/srv/SerializePoseGraph \
  "{filename: /home/alphayt/dev_ws/maps/my_new_map_serial}"
```

**5.** Point `map_file_name` at the new serialised map and set `mode: localization`
again.

> The mapping parameters here are tuned for detail over speed:
> `minimum_travel_distance: 0.1` m and `minimum_travel_heading: 0.1` rad
> (defaults are 0.5), with `map_update_interval: 1.0` s. This produces denser,
> more accurate maps at the cost of more CPU.

## Troubleshooting

**Robot does not move, no errors**
Check the controllers actually loaded:
```bash
ros2 control list_controllers
```
Both `diff_cont` and `joint_broad` must show `active`. If they are missing,
`controller_manager` probably failed to open `/dev/ttyUSB0`.

**`spawner` not found / controllers never spawn**
`launch_robot.launch.py` still calls `executable="spawner.py"`, which was renamed
to `spawner` in Humble. See [Known issues](#known-issues).

**No `/scan` topic**
```bash
ros2 topic hz /scan       # should be ~10 Hz
ls -l /dev/ttyUSB1
```
If the LIDAR enumerated as `ttyUSB0` instead, swap the ports or use a stable
device path.

**Stable device names (recommended)**
USB order can flip between boots. Pin them with a udev rule:
```bash
ls -l /dev/serial/by-id/          # find the stable identifiers
sudo nano /etc/udev/rules.d/99-robot.rules
```
```
SUBSYSTEM=="tty", ATTRS{idVendor}=="XXXX", ATTRS{idProduct}=="XXXX", SYMLINK+="ttyArduino"
SUBSYSTEM=="tty", ATTRS{idVendor}=="10c4", ATTRS{idProduct}=="ea60", SYMLINK+="ttyLidar"
```
Then reload with `sudo udevadm control --reload-rules && sudo udevadm trigger`
and update `ros2_control.xacro` and `rplidar.launch.py` to use `/dev/ttyArduino`
and `/dev/ttyLidar`.

**Robot localises onto the wrong part of the map**
Use **2D Pose Estimate** in RViz to place it correctly, then drive a short
distance so the scan matcher converges.

**TF errors: `map` frame does not exist**
`slam_toolbox` has not started or failed to load the serialised map. Confirm the
path in `mapper_params_online_async.yaml` points at files that exist — note it is
an **absolute** path and will be wrong on any machine where the workspace is not
at `/home/alphayt/dev_ws`.

**Odometry drifts / robot turns the wrong amount**
Re-measure `wheel_separation` and `wheel_radius` in `config/my_controllers.yaml`,
and verify `enc_counts_per_rev` in `description/ros2_control.xacro` against your
actual gearbox and encoder.

## Known issues

These are real defects in the current tree, left documented rather than silently
patched:

1. **`spawner.py` → `spawner`.** `launch_robot.launch.py` still uses the pre-Humble
   executable name `spawner.py` for both controller spawners. `launch_sim.launch.py`
   was already fixed. On Humble the real-robot launch will fail to spawn
   controllers until the same fix is applied.

2. **Wheel radius mismatch.** `config/my_controllers.yaml` sets
   `wheel_radius: 0.040` while `description/robot_core.xacro` sets `0.0415`. The
   controller uses the former for odometry, so reported distances are ~3.6% short.
   Pick one measured value and use it in both places.

3. **Bundled `navigation_launch.py` is outdated.** It references the
   `nav2_recoveries` package, renamed to `nav2_behaviors` in Humble.
   `bringup.launch.py` works around this by including `nav2_bringup`'s own launch
   file instead. Use `bringup.launch.py`, not the bundled copy.

4. **Absolute paths.** `map_file_name` in `mapper_params_online_async.yaml` is an
   absolute path under `/home/alphayt/dev_ws`. `slam_toolbox` does not expand ROS
   package paths in this parameter, so anyone cloning this repo elsewhere must
   edit it.

5. **`nav2_params.yaml` has `use_sim_time: True`** throughout. `bringup.launch.py`
   overrides it to `false` at launch, but running Nav2 directly from this file on
   hardware will hang waiting for a clock that never ticks.
